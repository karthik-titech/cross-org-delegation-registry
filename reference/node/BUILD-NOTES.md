# Node.js verifier build notes

- Draft Sections 3.2, 3.3, 4.1 and 10.4. The configured issuer ID in the root's `iss` selects the trust anchor and matches the consent fixture's `trust_anchor_kid`. The optional protected-header `kid` is a hint. The fixture configuration has one key per issuer.
- Draft Sections 4.1, 4.2 and 8.4. The Ed25519 profile implements no JOSE critical extension parameters. Child JWK import uses the validated public key members. The `sha256:` plus lowercase hex form applies to `narrowing_proof.hash` as well as `ceiling_ref`. Parent and invocation signing-input digests use unpadded base64url (Sections 4.2 and 6.1).
- Draft Sections 4.4 and 6.2. I-JSON parsing and integer range checks apply to JOSE protected headers and payloads. The parser reports Unicode noncharacters with the existing `syntax` reason. Arguments binding hashes JCS of the supplied request object, where `1e21` is serialized as `1e+21`.
- Draft Sections 4.5 and 5.3 steps 1 and 3, and Section 5.6. A nonnegative root depth and a string-array `parent_chain` pass the parse shape check. A signed root with a nonzero depth or a nonempty parent list fails linkage.
- Draft Sections 4.2 and 5.3 step 6, and Section 6.3 check 4. The fixture profile checks token and invocation times at the supplied instant, with inclusive `iat` and `nbf` (when present) and exclusive `exp`. Fractional NumericDate values are compared at the supplied instant's precision.
- Draft Sections 5.3, 8.1 to 8.4 and 10.3. Fixture effects stand in for parsing Cedar, and a missing or invalid effect gives `unsupported_fixture_policy`. A present token status claim stops at step 8 with `status_unknown`. Failed syntactic narrowing gives `mandate_not_narrower`.
- Draft Sections 5.3, 6.1, 6.3, 6.4 and 11.2. The invocation names one audience and the delegation token can name several. When holder binding begins, the fixture label lists the WPT assumption's covered fields in the order `Pedigree`, then `Pedigree-Invocation`, with each included field listed once and joined by `+`. If the assumption covers neither field, the label is `wpt_assumed:fresh,covers=`. The label reports the same coverage whether or not an invocation is present, including when binding fails. An absent assumption supplies no label.
- Draft Sections 6.3 and 12.7. Replay is checked using the audience, holder thumbprint and invocation `jti`. The verifier records the invocation as soon as check 5 passes. A failure in arguments binding or policy evaluation leaves the record in place.
- To report the outcomes in Draft Section 5.6, the fixture CLI uses `JSON.parse` for manifest, expected results, fixtures and case files. It checks each case digest against the raw bytes before parsing. If a parsed case cannot supply a verification result for an expected row, the CLI emits a failed row with `got: null` and empty trusted-input labels.
- Draft Section 4.1. The fixture profile adds the small-order public-key refusal. The verifier checks whether eight times the decoded point is the identity, covering all canonical small-order encodings after the point-decoding checks.
- Draft Sections 5.3, 6.3 and 10.4. Consent and CLI case timestamps share an RFC 3339 parser. Consent matching applies UTC offsets with integer arithmetic and compares fractional digits exactly after stripping trailing zeros. For each required consent ID, a matching revocation takes precedence over active answers. An invalid timestamp on a row for the required anchor and consent ID yields `status_unknown`. An invalid case timestamp yields CLI exit code 2. Library callers can supply RFC 3339 text for precision beyond the milliseconds available in a `Date`. Token and invocation time checks use numeric seconds. Leap seconds in RFC 3339 input are validated against the built-in IERS dates through December 2016.
- Draft Sections 5.3 and 7.2. Fixture loading and step 11 after the grant check validate the decision rows using the same exact policy ID, action, resource and canonical arguments key. Repeated rows with the same decision are accepted. Contradictory rows raise `FixtureError` on load or yield `unsupported_fixture_policy` during step 11 fixture validation.
- Draft Sections 5.3, 7.1 and 7.2. Step 7 hashes every configured ceiling byte array and checks its key before checking chain membership. Once the step 11 grant check passes, the leaf's configured ceiling bytes must equal JCS of the fixture ceiling. Either byte validation failure yields `unsupported_fixture_policy`.
- Draft Sections 5.3, 6.3 and 12.6. The library requires positive safe integers for all three limits and throws `TypeError` before processing when a limit is absent or invalid.
- Draft Sections 5.3, 7.2 and 8.3. A chain with a mandate records `policy_fixture` first, when step 5 consults fixture effects. Step 11 checks grant coverage before reading the policies fixture. A mandate-free chain that fails the grant check returns `scope_not_granted` with `consent_fixture` and the WPT label. Once the grant check passes, step 11 validates decision rows and fixture ceiling bytes before looking up any decision. A mandate-free chain records `policy_fixture` at that first fixture read, after `consent_fixture` and the WPT label.

The verification gate ran on Node v25.9.0 with OpenSSL 3.6.2. The implementation uses Node 20 standard library APIs.
